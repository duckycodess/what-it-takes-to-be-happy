# Foundation implementation plan (#3)

This is the bounded implementation plan for the static essay foundation, not the final narrative or reader design.

**Historical.** This plan was written and executed before the 9 October owner amendment, which made the hosted site the deliverable and discontinued the offline HTML submission. It is kept as a record of what #3 set out to build and did build. Its offline requirements described the brief at the time; [the amendment](decisions.md#owner-amendment--9-october-2026) governs now.

1. **Authoring contract.** Store explicitly labeled non-final fixture data as local JSON with stable slug IDs for chapters, scenes, cast, sources, optional details, interactions, and provenance. Require chapter opening/closing connections, source review status, and cast expressions; use fictional fixture speakers rather than invented TJ/Koj/Vier statements. Keep scene order explicit in chapter `sceneIds`; references use IDs, never array offsets. Express essential text, dialogue, visual descriptions, concepts, evidence, and visible limitations independently of optional details. Separate authoring provenance from published fields. Document every field and how later editorial deltas map to IDs. Do not imply the fixture is a researched claim or member-endorsed position.
2. **Validation.** A dependency-light Node validator checks shape/required strings (including chapter connections, source review status, expressions), missing and duplicate IDs, cross-registry references (including speakers and dialogue sources), chapter ownership, scene ordering/coverage, invalid optional interactions and static equivalents, and empty essential scenes. Return actionable location-specific errors and a nonzero exit code; exercise invalid fixtures and valid reordering by stable IDs in tests.
3. **Shared outputs.** Use a small static HTML/CSS/JS runtime with content embedded at build time. One renderer consumes validated content for a minimal presentation fixture and a continuous reading/print entry point. A deterministic build emits Vercel-ready `dist/index.html` and directly opened self-contained `dist/offline.html`; no runtime fetches or external required resources. Inline an existing committed original concept illustration and a locally committed open-licensed temporary font (with license/provenance) as data URIs to prove binary packaging, explicitly not a final font/art choice. Assert no required-resource external or relative src/href/url() links in offline output. Provide a local preview server and a single-file export command; no backend or framework. Future #5 owns full reader interactions and #7 owns release.
4. **Verification and handoff.** Document real `npm` commands and rationale in README/architecture and record exact Vercel root/install/build/output settings in docs/delivery.md. Commit a lockfile and pinned Node version for reproducibility; automated validator/navigation/output tests plus actual preview smoke. Open the offline artifact at `file://` with networking disabled and exercise the fixture and reading view (or report precise browser tooling limitation). Confirm HTML contains all essential data and no authoring provenance jargon. Keep the minimum UI accessible and usable at mobile width with semantic controls, visible keyboard focus, and sensible reading order; no finished artwork, final prose, or invented evidence.

Implementation batches: first contract/validator/tests; second shared runtime/build/preview/docs/offline verification. Run tests and deterministic checks before final review. The independent reviewer first checks this plan for scope and contract gaps, then reviews the exact pushed head after final verification. Only substantive BLOCKER/IMPORTANT findings require changes and scoped re-review.
